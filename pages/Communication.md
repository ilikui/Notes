# 车载通信技术总览

车载通信需要同时考虑物理介质、链路层、网络/传输机制、应用协议、实时性、诊断与故障恢复。选择技术时，应依据带宽、时延、确定性、拓扑、成本和安全要求，而不是只比较峰值速率。

- [[CAN]]：控制器局域网，常用于控制报文与诊断
- [[LIN]]：低成本、低速、主从式子网
- [[FlexRay]]：面向确定性时序的车载网络技术，实际项目需确认采用情况
- [[Ethernet]]：高带宽车载网络，可承载多种上层协议
- [[AUTOSAR]]、[[Communication Stack]]：从应用信号到总线报文的软件链路

## 从应用数据到物理总线

```mermaid
flowchart LR
    A[SWC Signal] --> B[RTE]
    B --> C[COM]
    C --> D[PduR]
    D --> E[CanIf / EthIf / LinIf]
    E --> F[MCAL Driver]
    F --> G[Controller / Transceiver]
    G --> H[Physical Bus]
```

此图用于理解典型发送方向，实际模块组合随总线类型、AUTOSAR 版本和供应商实现而变化；接收方向通常沿相反方向传递，并包含解包、路由和信号更新。

## 报文问题的分层定位

1. **应用层**：信号值是否更新？Runnable 是否执行？数据类型和更新周期是否正确？
2. **通信服务层**：COM 是否打包？PDU 是否启用？路由与通信模式是否正确？
3. **接口/驱动层**：控制器是否初始化？邮箱、过滤器、缓冲区和错误状态是否正常？
4. **物理层**：供电、接地、终端电阻、线束、收发器和波形是否正常？
5. **系统层**：总线负载、错误计数、Bus-Off、超时、唤醒和休眠是否符合预期？

## 实验记录建议

记录报文 ID、周期、DLC/长度、信号定义、预期值、实际值、时间戳、总线负载、错误计数和测试条件。不要只凭单次抓包推断系统稳定性。
